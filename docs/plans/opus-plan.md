# Opus 5 plan — Unified Inbox backend

Treats existing scaffolding as fixed (schema with load-bearing indexes `sends.by_user_idempotency_key` and `connections.by_user_provider_account`; core/types verbatim spec contract; core/http retryTransient refusing permanent/needs_reconnect/unknown; AES-GCM crypto on Web Crypto; faults gated by ALLOW_FAULT_INJECTION; complete gmail adapter with 403 disambiguation). Everything additive except convex/http.ts routes, six schema fields, UI glue.

## 1. Architecture

### 1.1 OAuth: start in an authenticated Convex mutation, finish in a Convex HTTP action
No Next.js route handlers in OAuth at all. `useMutation(api.oauth.begin)({provider, reconnectConnectionId?, returnTo})` → inserts oauthStates row {state, userId, provider, codeVerifier, expiresAt}, returns authorize URL → browser navigates → provider 302s to `https://<slug>.convex.site/oauth/<provider>/callback` (httpAction) → atomically consume state, exchange code, fetch identity, encrypt tokens, upsert on (userId, provider, externalAccountId) → 302 to `${APP_BASE_URL}${returnTo}`.

Why: (1) callback needs DB + encryption key, both live in Convex; no provider secret or token ever exists in the Next process. (2) redirect URI is stable regardless of where the frontend runs — localhost, Codespaces (unpredictable hostname), Vercel. (3) start is a normal authed Convex mutation, so no JWT in query strings; callback recovers user from the state row.

Details: state consumption is a single internalMutation (read by_state, check consumedAt/expiresAt, patch consumedAt, return row) — replay gets 400. PKCE S256 for Google; Slack oauth.v2.access does not support PKCE (state only). `returnTo` allowlisted to a path, always prefixed with APP_BASE_URL (open-redirect defense). Reconnect: upsert on triple keeps `_id` so drafts/sends/results connectionIds stay valid; if reconnectConnectionId set and returned externalAccountId differs → reject with specific "you signed in as bob@, this connection is alice@" error; Google gets login_hint=<accountEmail> on reconnect.

### 1.2 Token refresh: refresh-on-use, single-flight, never on a cron
`resolveToken(connectionId)` helper called inside actions: seed connection → permanent error; revoked → needsReconnect; expiry > now+120s → decrypt and return; else acquire refresh lease (`refreshLockedUntil = now+30s` via mutation — single-flight; loser sleeps 250ms and re-reads, bounded 3 tries), POST token endpoint, success → store re-encrypted token + expiry + status active + clear lease; invalid_grant/token_revoked → markRevoked (status revoked, verbatim statusReason) + throw needsReconnect; 5xx/429 → clear lease + transient. The 120s skew window refreshes before a 401, and silent refresh is demonstrated on the read path too. Lease matters because fan-out over two Gmail accounts + concurrent send can hit one connection thrice; under Slack rotation it becomes a correctness requirement.

### 1.3 Fan-out: one scheduled action per source-connection
`api.searches.run` (mutation): insert searches{running}, resolve targets (one per enabled connection of requested providers + one web), insert searchSources{pending}, `scheduler.runAfter(0, internal.orchestrator.runSource, {searchSourceId, demo})` per target, plus `runAfter(DEADLINE+5s, sweepSearch)`. Each runSource is a separate Convex action — own isolate, transaction boundary, failure domain; a crash kills one source, not the fan-out.

runSource: beginSourceRun mutation (running, startedAt, attemptCount++) → resolveToken → adapter via retryTransient (3 attempts, jitter, onRetry bumps attemptCount) with `AbortSignal.timeout(20s)` and artificialDelayMs from demo → completeSourceRun as ONE mutation: insert all searchResults (scored, capped 20), patch searchSources succeeded + counts + duration, patch searches.resultCount, and if no sibling pending/running flip searches complete (race-safe sibling check). Failures → failSourceRun: needs_reconnect is its own terminal status, else failed with errorKind + full message. sweepSearch watchdog forces anything still pending/running past deadline to failed/transient "worker did not report"; cron backstop every 5 min. UI can never spin forever.

### 1.4 Partial results = one reactive query
`api.searches.watch({searchId}) → {search, sources[], results[] (arrival order)}`. Convex reactivity is the streaming mechanism — no SSE/polling. Ordering: arrival order during a run (append, never re-sort — keeps rows stable under the reader); rank exists as write-time `score` (recency + source weight + term hits, `core/rank.ts`), results ranked within each arriving batch; REST exposes `?order=rank|arrival` (default rank — an agent has no cursor to protect). Cap 20/source keeps completeSourceRun inside transaction limits.

### 1.5 Send gate
Three distinct calls; no function anywhere accepts recipient+body and sends.
draft → POST /drafts/{id}/confirm {reviewedHash} (server re-derives sha256(canonical(draft)); mismatch = 409 PAYLOAD_MISMATCH; any edit → back to draft, hash cleared) → POST /drafts/{id}/send → sends.claim.

sends.claim (one mutation — THE guarantee): load owned draft; status draft → CONFIRMATION_REQUIRED; re-derive canonical hash, mismatch → PAYLOAD_CHANGED_SINCE_CONFIRM; indexed `.unique()` read on sends by_user_idempotency_key(userId, idempotencyKey) → existing → return {sendId, claimed:false}; else insert frozen send {queued, attemptCount 0, maxAttempts 4, payload copied from draft} → {claimed:true}; only claimed:true schedules delivery.

Race-safety, precisely: Convex mutations are serializable ACID transactions under OCC. The indexed range read puts (userId, idempotencyKey) in the read set; a concurrent insert into that range invalidates the loser, Convex auto-retries it, and on retry it sees the row → claimed:false. Exactly one claimant. Two traps: must be an indexed range read on the full key (filter/table scan = correct but conflicts with everything; draftId read = no conflict at all when two drafts share a key), and read+insert must be in the SAME mutation (query-then-mutation or action-side check reintroduces the race).

deliver: beginAttempt mutation (succeeded → skip already_delivered; in_flight → skip attempt_in_progress (lease — mashing retry is a no-op); unknown → skip indeterminate, NEVER auto-retried; exhausted for auto trigger → skip; else in_flight, attemptCount++, insert sendAttempts row) → resolveToken → SENDERS[channel].send with 20s timeout + injectFailure → finishAttempt (succeeded + providerMessageId; drafts → sent) / failAttempt by kind:
- transient: attempts < max → failed_transient + nextRetryAt + scheduler.runAfter(backoffMs(n), deliver, {trigger:"auto"}); else failed_transient, nextRetryAt cleared, operator decides.
- permanent: failed_permanent, draft → failed, no retry.
- needs_reconnect: send needs_reconnect + connection revoked; draft STAYS confirmed so reconnect-then-retry works with the SAME key.
- unknown: status unknown, no retry ever.

Unknown handling: cron (1 min) sweeps in_flight sends whose latest attempt started >90s ago → unknown (honest "we don't know", not failed_transient). Operator UI: "retrying could send a second copy" with (1) Reconcile — reads only: Gmail sends carry X-Unified-Inbox-Key header + deterministic Message-ID derived from the key, so `q=rfc822msgid:` resolves unknown → succeeded/failed_permanent; Slack via conversations.history scan; (2) Send anyway — requires cloning the draft with a NEW key; an unknown row is never reused under the same key. Neither provider offers server-side idempotency on send — state plainly.

Confirm friction: create returns no send affordance; confirm requires reviewedHash obtainable only from the reviewPayload query (proves the payload was rendered); claim re-derives; send on unconfirmed = 409; no one-shot entry point exists — a test snapshots the public function list to guard this.

### 1.6 Module boundary
core/* (contracts, crypto, http, faults, rank, registry — no Convex imports, unit-testable) / adapters/* (only place knowing provider shapes) / orchestrator+drafts+sends internal functions (no auth logic; take userId as arg — the shells are the authorization boundary, documented since it superficially violates the guideline) / two thin auth shells: public Convex functions (Clerk) and REST http routes (API key). UI pure consumer. "Search and send entirely through the API with no UI" true by construction.

## 4. Slack specifics
User token (xoxp) only; search.messages rejects bot tokens (not_allowed_token_type); post with user chat:write so replies appear as the user (no bot invite needed). externalAccountId = `${team.id}:${authed_user.id}` (schema's documented format), label = team.name.
Revocation: Slack returns HTTP 200 {ok:false,error} — fetchJson only throws on non-2xx, so adapter must check ok itself. classify: needs_reconnect {token_revoked, invalid_auth, not_authed, account_inactive, token_expired, missing_scope, no_permission}; transient {ratelimited (+Retry-After), service_unavailable, internal_error, fatal_error, request_timeout}; permanent {channel_not_found, not_in_channel, is_archived, msg_too_long, invalid_arguments, restricted_action, cannot_dm_bot}; unrecognized → permanent.
Rate limits: search Tier 2 (~20/min), postMessage ~1/s/channel — fine for demo. Rotation disabled but refresh branch written and gated on refreshTokenCipher presence.
Normalization from matches[]: id=ts, title="#channel", snippet=text (strip <@U…|name>, <url|label> mrkdwn), author=username, timestamp = ts×1000 → ISO (ts is SECONDS.micros — the classic 1970 bug), url=permalink, threadId=thread_ts??ts, replyTo=channel.id.
Risk: verify search.messages availability on the workspace plan day 1; fallback = conversations.list + history sweep behind the identical interface.

## 5. Gmail OAuth specifics
Authorize: access_type=offline AND prompt=consent (re-grant returns NO refresh_token otherwise — the #1 multi-account Gmail bug), include_granted_scopes=false, PKCE S256, login_hint on reconnect. On exchange, KEEP existing refreshTokenCipher if response omits one — never overwrite good refresh token with undefined.
Refresh failure {"error":"invalid_grant"} = canonical revoked signal → status revoked + verbatim reason + needsReconnect.
Identity: userinfo → {sub, email}; externalAccountId = email (matches schema comment + authuser permalink; sub is the immutable production choice — documented tradeoff).
Testing-mode warnings for README: restricted scopes work only for Test users + unverified interstitial (screenshot it); refresh tokens EXPIRE AFTER 7 DAYS in Testing status — makes needs_reconnect a routine demonstrable event; lead the demo with it; re-grant before recording.
Revocation demo paths: (1) connections.simulateRevoke (fault-gated, garbles ciphers — real 401 path), (2) POST oauth2 /revoke, (3) myaccount.google.com/permissions (show on camera).
